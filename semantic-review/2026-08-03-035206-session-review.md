# Stock sync, billing revoke, and bar delete session review

This session wired up a DB trigger to keep `actual_qty` in sync with `stock_qty` changes, added open-bottle/pack display to the stock-check page, completed the billing revoke/approve realtime flow, hardened the revoke edge function to cover all plan types, fixed `setUserStatus` to reset billing fields on pending transitions, added realtime to the admin billing page, and reworked bar deletion to decrement the right counter (`addon_bar_count` vs `chain_bar_count`). The addon-bar creation function switched from incrementing a cached count to re-counting sub-accounts from DB.

Watch for: **(confirmed)** `loadOpenItems` silently overwrites a bottle entry with a pack entry when both tables return the same `product_id` — the bottle data is lost; **(confirmed)** `admin-revoke-plan` full reset deletes cashiers but not managers — manager auth accounts survive revoke; **(confirmed)** `setUserStatus` applies the full billing reset to any profile ID passed in, including cashiers and managers with `parent_id` set; **(confirmed)** the "navigate home if no bars remain" check in `SwitchBarPage` reads stale `chainBars` closure state after `refreshBars()` and may fail to redirect; **(confirmed)** `create-addon-bars` Case 2 (upgrade existing sub-account) does not increment `addon_bar_count`, creating a counter asymmetry with the delete path.

---

## High-level view

The `GREATEST(0, ...)` clamp in the trigger prevents negative `actual_qty`, but it also silently absorbs the over-delta when a sale exceeds the current `actual_qty`. When the floor is hit, the discrepancy gap widens by however much the delta exceeded the current value — the comment's claim that "the gap is preserved" is inaccurate in that case, and the stock-check loss display will overreport.

The stock-check page loads open bottles and open packs in parallel and merges them into a single `product_id`-keyed map. The pack loop runs second, so any product that appears in both tables loses its bottle entry entirely — the UI shows pack state, the remaining-units count is wrong, and the loss column is suppressed.

`admin-revoke-plan` now covers `machines_only_20` and `premium_20` in the full-reset path and all five addon types in the partial-reset path. The remaining gap is that step 1 only queries `role=cashier`; manager accounts (`role=manager`) are not cleaned up and their auth sessions remain live after revoke.

`setUserStatus` writes `plan_type: "basic"`, `addon_bar_count: 0`, `is_multi_bar: false`, and nine other billing fields whenever the target status is `pending`. Nothing in the function prevents passing a cashier or manager `user_id`, which would corrupt that sub-account's profile with owner-level billing fields.

The `SwitchBarPage` `deletedIds` set handles the immediate-removal UX correctly — the card vanishes and the count badge updates before `refreshBars()` resolves. The only stale-state problem is the post-delete navigation check, which reads `chainBars` from the closure (pre-delete snapshot) rather than from the result of `refreshBars()`.

`create-addon-bars` Case 2 (upgrading an existing sub-account by adding screens or a bar) updates the sub-account profile and marks the owner `is_multi_bar=true`, but does not touch `addon_bar_count`. Since `delete_bar_account` always decrements `addon_bar_count` for non-chain plans, deleting a Case-2-upgraded account will undercount by 1 compared to what was actually incremented.

<summary>Issues (6)</summary>

1. **`loadOpenItems` bottle/pack collision** — if a product has both an open bottle row and an open pack row, the pack entry overwrites the bottle silently. The UI shows the wrong open-item type, the remaining-units cell is wrong, and the loss column is suppressed for the bottle. Add a conflict guard or prefer whichever entry is more recent.

2. **`admin-revoke-plan` does not delete managers on full reset** — the cashier-cleanup query filters `role=cashier` only. Managers (`role=manager`) survive revoke with active auth sessions still linked to the now-pending owner. Expand the filter to `.in("role", ["cashier", "manager"])`.

3. **`setUserStatus` applies billing reset to non-owner profiles** — no role guard. A cashier or manager `user_id` passed in will have `plan_type: "basic"`, `addon_bar_count: 0`, `is_multi_bar: false`, etc. written onto a sub-account profile. Guard the billing-field block with a check that `parent_id IS NULL` (i.e., the row is actually an owner), or add the guard in the calling UI.

4. **`SwitchBarPage` stale `chainBars` in nav-redirect check** — `chainBars.filter(b => b.id !== deleteTarget.id)` reads the pre-delete closure snapshot after `refreshBars()` has already been awaited. Derive the post-delete remaining count from `profile?.addon_bar_count` after `refreshProfile()` resolves, or use whatever `refreshBars()` returns.

5. **`GREATEST(0,...)` clamp breaks the "gap preserved" invariant** — when the clamp fires, `actual_qty` floors at 0 but `stock_qty` continues to the actual low value, widening the discrepancy. The trigger comment says the gap is preserved; it isn't when the floor is hit. Stock-check will overreport loss in those cases. Document the actual behavior.

6. **`create-addon-bars` Case 2 skips `addon_bar_count` increment** — upgrading an existing sub-account sets `is_multi_bar=true` on the owner but never increments `addon_bar_count`. `delete_bar_account` will still decrement it, leaving the count one lower than the actual live sub-account total. Either increment in Case 2, or make the delete RPC re-count from DB the same way creation now does.

### `loadOpenItems` silent overwrite on dual-open products

```typescript
for (const row of bottlesRes.data ?? []) {
  map[row.product_id] = { type: "bottle", ... };
}
for (const row of packsRes.data ?? []) {
  map[row.product_id] = { type: "pack", ... };   // overwrites bottle
}
```

Both loops write to the same `product_id` key with no collision check. The pack loop runs second, so any product with a concurrent open-bottle and open-pack row renders as a pack. The bottle's `unitsSold` is discarded, `remaining` is computed from the pack's `units_sold`, and the loss column shows `—`. Whether this can happen depends on whether the schema enforces mutual exclusivity between `opened_bottles` and `opened_packs` for a given product — if it doesn't, this is a latent display bug waiting on a data edge case.

### `SwitchBarPage` stale `chainBars` in the nav-redirect check

```typescript
await Promise.all([refreshBars(), refreshProfile()]);
toast.success(`"${deleteTarget.name}" deleted`);
const remaining = chainBars.filter(b => b.id !== deleteTarget.id);
if (remaining.length === 0) { nav("/register"); }
```

`chainBars` is the closure value from the render that triggered `handleDeleteConfirm`. Even after `refreshBars()` resolves, the state flush is asynchronous — this closure still holds the pre-delete snapshot. For the common case (owner with 2 bars deletes one), `remaining` will contain the other bar and the redirect correctly won't fire. The failure mode is when the owner deletes their last deletable bar and `chainBars` happened to be stale before the delete — the redirect to `/register` won't happen. Using `profile?.addon_bar_count` after `refreshProfile()` gives a stable post-delete signal.

### `admin-revoke-plan` manager gap on full reset

```typescript
.eq("parent_id", ownerId)
.eq("role", "cashier")
```

Managers provisioned with `role=manager` are not matched. Their auth accounts remain active, their profiles stay linked to the revoked owner, and they retain whatever app access their role grants. The fix is straightforward: change `.eq("role", "cashier")` to `.in("role", ["cashier", "manager"])`. If managers can also have `role=owner` with `parent_id` set, the query would need to cover that too — worth confirming against how manager creation works.

### `create-addon-bars` Case 2 missing `addon_bar_count` increment

Cases 1 and 3 end with `addon_bar_count` explicitly set (Case 3 via DB re-count, Case 1 via owner plan upgrade that implies count is already correct). Case 2 — upgrade existing sub-account — updates the sub-account and marks `is_multi_bar=true` on the owner but leaves `addon_bar_count` unchanged. Since the delete RPC decrements it unconditionally for non-chain plans, each Case 2 upgrade followed by a delete silently decrements the counter by 1 below the true count. The cleanest fix aligning with the already-established pattern is to make `delete_bar_account` re-count from DB (same as `create-addon-bars` now does), rather than decrement — then the asymmetry disappears entirely.
